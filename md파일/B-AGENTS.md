# B-AGENTS.md

## 1. 목적
이 문서는 착한코드검거단 프로젝트에서 팀원 B 또는 B를 돕는 AI 에이전트가 따라야 할 행동 규칙을 정의한다.

본 문서는 원본 `AGENTS.md`의 하위 문서이며, 충돌 시 원본 문서가 우선한다.

이 문서의 목표는 두 가지다.

1. B가 작업 중 범위를 벗어나지 않도록 막는다.
2. AI가 코드를 생성할 때 B의 역할과 금지사항을 명확히 이해하게 한다.

## 2. 역할
B의 책임은 다음 네 가지다.

1. Shared Contract 동결
2. AST 기반 Core Infrastructure 구현
3. 규칙 연결 구조 제공
4. 결정적 JSON 결과 기반 제공

추가로 B는 팀 전체의 계약 관리자 역할도 가진다.  
즉, B는 구현자이면서 동시에 "어디까지가 공용 약속인지"를 고정하는 사람이다.

## 3. 최우선 규칙
### R1. 문서 우선순위 준수
항상 다음 우선순위를 따른다.

1. `PRD.md`
2. `AGENTS.md`
3. `plan.md`
4. `B-PRD.md`
5. `B-AGENTS.md`
6. `B-plan.md`

### R2. 대상 파일 비실행
다음 행위는 금지한다.

1. 대상 Python 파일 실행
2. 대상 Python 파일 import
3. `exec`, `eval`, `runpy`, `importlib` 등을 통한 간접 실행
4. subprocess를 통한 대상 파일 실행

분석은 텍스트 읽기와 `ast.parse(...)`로만 수행한다.

이 규칙은 단순 권장사항이 아니라 B 범위의 핵심 불변식이다.  
코드, 테스트, 리뷰 모두 이 규칙을 기준으로 판단한다.

### R3. 범위 준수
B는 core/shared contract/AST infrastructure에 집중한다.
GUI, 개별 규칙 로직, 최종 빌드 흐름은 직접 범위가 아니다.

다만 통합 호환성을 위해 인터페이스는 고려해야 한다.  
즉, B는 GUI를 만들지 않지만 GUI가 호출하기 어려운 API를 만들어서도 안 된다.

### R4. 계약 우선
구현보다 계약을 먼저 고정한다.
`Finding`, `ScanResult`, `Rule`, `scan_file(...)`를 먼저 정의한 뒤 구현한다.

계약이 흔들리면 A/C/D 작업이 흔들리므로, 구현 편의보다 계약 안정성을 우선한다.

### R5. 결정성 유지
다음은 분석 결과에 사용하지 않는다.

1. 현재 시간
2. 랜덤값
3. 네트워크 응답
4. 환경에 따라 달라지는 값

추가 금지 예시:

1. 비정렬 dict 순회 결과에 의존하는 출력
2. OS 상태에 따라 달라지는 임시 식별자
3. 분석 시점에 따라 달라지는 부가 메타데이터

### R6. 최소주의
B는 처음부터 완벽한 프레임워크를 만들려고 하지 않는다.
현재 P0 범위를 만족하는 최소 구조를 우선 구현한다.

### R7. 설명 가능한 구조
B가 만드는 공통 구조는 문서 없이도 어느 정도 읽히는 수준이어야 한다.
이름, 함수 경계, 테스트 이름이 역할을 설명해야 한다.

## 4. 허용 작업
다음 작업은 허용된다.

1. 공통 타입/데이터 구조 정의
2. AST 파싱 파이프라인 구현
3. 규칙 실행 registry 또는 동등 구조 구현
4. source snippet helper 구현
5. JSON 직렬화 보조 구현
6. core 테스트 작성
7. 계약 검증용 fixture 작성
8. 규칙 개발자가 참고할 샘플 규칙 스켈레톤 작성
9. 통합을 위한 얇은 validation 보조 작성

## 5. 금지 작업
다음 작업은 금지한다.

1. 전체 안전성 점수 추가
2. "안전하다/취약하다" 판정 로직 추가
3. 폴더/프로젝트 단위 분석 추가
4. 담당 외 파일 광범위 수정
5. 규칙별 특수 케이스를 core에 하드코딩
6. 근거 없이 계약 필드 확대
7. 조용히 예외를 삼켜 디버깅을 어렵게 만드는 구조
8. "미래 확장성"만 이유로 과도한 추상 계층 추가
9. 공용 계약에 UI 전용 표현 필드 섞기
10. 규칙 작성 편의라는 이유로 core에서 대상 파일 재접근 허용

## 6. 구현 행동 규칙
### G1. 최소 계약
가능한 한 작은 계약으로 시작한다.

권장 최소 Finding 필드:
- `rule_id`
- `line`
- `code`
- `message`

권장 최소 ScanResult 필드:
- `target_file`
- `findings`

필드 추가 기준:

1. 현재 소비자가 실제로 필요한가
2. 결정성을 해치지 않는가
3. 규칙 구현자와 GUI 담당이 동시에 이해 가능한가
4. 테스트로 고정 가능한가

### G2. 규칙 인터페이스 단순화
규칙 구현자는 최소 입력만 받아야 한다.

권장:
- AST
- source helper

반환:
- `list[Finding]`

규칙 인터페이스 설계 시 지켜야 할 점:

1. 규칙이 파일 시스템이나 네트워크에 의존하지 않게 한다.
2. 규칙이 반환 형식을 임의로 바꾸지 못하게 한다.
3. 규칙 구현이 source helper 없이 불편하면 helper를 개선하고 interface는 유지한다.

### G3. 단일 진입점 유지
스캐너는 단순한 entrypoint를 제공해야 한다.

권장 예:
- `scan_file(path)`

가능하면 호출자가 내부 registry, parser, serializer를 모두 몰라도 되게 설계한다.

### G4. 공용 helper 제공
C/D가 반복 구현하지 않도록 아래를 우선 제공한다.

1. 소스 줄 조회
2. node 기반 코드 스니펫 조회
3. finding 생성 시 필요한 최소 유틸
4. AST node에서 근거 코드를 복원하는 일관된 방식

### G5. 정렬 규칙 명시
findings는 명시된 기준으로 정렬한다.

권장 기준:
1. line
2. rule_id
3. code

정렬 기준은 테스트로 고정한다.  
"지금은 우연히 같은 순서"인 상태를 허용하지 않는다.

### G6. 예외 처리 원칙
기본적으로 규칙 버그는 숨기지 않는다.
통합을 위해 예외를 포착하더라도, 디버깅 가능한 형태와 정책을 먼저 문서화한다.

### G7. 샘플 우선
구조가 애매하면 문서 설명만 늘리지 말고 더미 규칙, 더미 결과, 더미 fixture로 예시를 만든다.

## 7. 테스트 규칙
B는 변경마다 아래 종류의 테스트를 우선 고려한다.

1. 빈 규칙 세트에서 스캐너 동작 테스트
2. no-execution invariant 테스트
3. finding 정렬의 결정성 테스트
4. JSON 구조 결정성 테스트
5. source snippet 추출 테스트

테스트가 없다면 core 변경은 완료로 보지 않는다.

추가 원칙:

1. 테스트 이름만 읽어도 core 계약을 이해할 수 있어야 한다.
2. fixture는 가능한 한 짧고 의도가 분명해야 한다.
3. 테스트는 규칙 내용보다 contract와 invariant를 우선 보호해야 한다.

권장 최소 검증 질문:

1. 이 테스트가 no-execution을 지키는가
2. 이 테스트가 JSON 결정성을 보호하는가
3. 이 테스트가 다른 팀원의 사용 방식을 보여주는가

## 8. 협업 규칙
### C와의 협업
- Rule contract가 GOOD001~GOOD003 구현에 무리가 없는지 확인한다.
- 규칙 구현 부담을 core가 키우지 않도록 한다.
- 규칙 예시 하나로 C가 바로 시작할 수 있게 한다.

### D와의 협업
- GOOD004~GOOD006 연결 시 registry가 충분한지 확인한다.
- JSON export가 ScanResult 계약과 충돌하지 않는지 확인한다.
- 통합 과정에서 필요한 contract translation이 생기지 않도록 한다.

### A와의 협업
- GUI가 호출할 API를 지나치게 복잡하게 만들지 않는다.
- 에러/빈 결과 형태가 UI에서 다루기 쉬운지 확인한다.
- GUI가 얇은 adapter만으로 core를 사용할 수 있게 한다.

## 9. 보고 규칙
작업 종료 시 아래를 공유한다.

1. 오늘 작업 범위
2. 변경 파일
3. 공통 계약 변경 여부
4. 테스트 결과
5. 담당 외 영역 수정 여부
6. 남은 리스크

가능하면 아래 두 줄도 함께 포함한다.

1. 다른 팀원이 바로 사용할 수 있는 공용 인터페이스 요약
2. 계약 변경이 있었다면 영향 받는 팀원

## 10. 리뷰 체크리스트
코드 리뷰 전 반드시 아래를 확인한다.

1. 대상 파일을 실행하는 경로가 없는가
2. 계약이 불필요하게 커지지 않았는가
3. 규칙별 특수 로직이 core에 새지 않았는가
4. 결과가 결정적인가
5. fixture와 테스트가 함께 갱신되었는가
6. helper가 규칙 작성 난이도를 실질적으로 낮추는가
7. API가 GUI와 JSON export에 과한 부담을 주지 않는가

## 11. 병합 전 체크
1. A가 호출할 entrypoint가 안정적인가
2. C/D가 rule만 추가해도 붙는가
3. JSON 구조가 동결 가능한가
4. 테스트가 core 회귀를 잡을 수 있는가
5. 문서와 코드가 서로 어긋나지 않는가

## 12. AI에게 직접 줄 수 있는 행동 지침
이 문서를 읽은 AI는 다음 방식으로 행동해야 한다.

1. 먼저 공통 계약을 요약한다.
2. 그다음 core 범위 안에서만 구현 계획을 세운다.
3. 대상 파일 비실행 원칙을 명시적으로 확인한다.
4. 최소 구현과 테스트를 함께 제안한다.
5. 담당 외 영역은 수정하지 않고 필요한 경우 제안만 남긴다.

## 13. B를 위한 금지 문장 해석
다음과 같은 말은 B 작업에서 경계해야 한다.

1. "나중에 필요할 수도 있으니 일단 넣자"
2. "GUI에서 편하니까 core에 필드를 더 넣자"
3. "규칙마다 좀 다르니 core에서 분기 처리하자"
4. "예외는 그냥 무시하고 계속 돌리자"

이런 문장은 대부분 contract drift, 과설계, 디버깅 비용 증가로 이어진다.
