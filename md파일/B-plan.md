# B-plan.md

## 1. 목적
이 문서는 착한코드검거단 프로젝트에서 팀원 B가 실제로 따라야 할 작업 순서, 완료 조건, 보고 형식을 정의한다.

원본 `plan.md`를 대체하지 않으며, B가 실수 없이 core 작업을 끝내기 위한 실행용 문서다.

## 2. B의 핵심 임무
1. 공통 계약을 먼저 동결한다.
2. AST 기반 스캐닝 스켈레톤을 만든다.
3. 규칙이 붙는 확장 지점을 만든다.
4. 결과 JSON의 결정성을 보장한다.
5. no-execution invariant를 테스트로 보호한다.

## 3. 선행 조건
작업 시작 전에 아래를 완료해야 한다.

1. `PRD.md` 읽기
2. `AGENTS.md` 읽기
3. `plan.md` 읽기
4. B 소유 파일과 변경 금지 영역 확인
5. 브랜치 전략 확인

추가 확인:

1. 공통 계약을 먼저 올릴지, 코드와 함께 올릴지 팀 합의가 있는지
2. JSON 결과를 누가 소비하는지 명확한지
3. GUI가 어떤 entrypoint를 기대하는지 대략 공유됐는지

## 4. 브랜치 순서
### 1단계
최초 공통 계약은 `chore/foundation-contract`에서 작성한다.

### 2단계
공통 계약이 검토되고 main에 병합된 뒤, B의 주 작업은 `feat/core`에서 이어간다.

### 3단계
병합 중 계약 충돌이 생기면 구현을 밀기보다 계약부터 재확인한다.

## 5. 작업 단계
### Phase 1. 계약 동결
목표:
- 다른 팀원이 참고할 수 있는 공통 타입과 인터페이스를 확정한다.

할 일:
1. `Finding` 필드 초안 작성
2. `ScanResult` 필드 초안 작성
3. `Rule` 인터페이스 초안 작성
4. `scan_file(...)` 입출력 정의
5. JSON 예시 작성
6. findings 정렬 기준 정의
7. 스니펫 복원 전략 정의

완료 조건:
1. 문서와 코드 중 최소 한 곳에 계약이 명시돼 있다.
2. C/D가 규칙 구현 시작이 가능하다.
3. A/D가 결과 구조를 이해할 수 있다.
4. "이 필드가 왜 필요한지" 설명할 수 있다.

### Phase 2. AST Infrastructure
목표:
- 단일 파일 입력을 안전하게 AST로 분석하는 core 흐름을 만든다.

할 일:
1. 파일 읽기
2. `ast.parse(...)`
3. source helper 구성
4. rule registry 또는 동등 구조 구현
5. findings 수집 및 정렬
6. ScanResult 반환
7. 스니펫 또는 줄 단위 근거 코드 복원

완료 조건:
1. 빈 규칙 또는 더미 규칙으로 스캐너가 실제 동작한다.
2. 대상 파일 실행 없이 결과가 생성된다.
3. 규칙 추가 지점이 명확하다.
4. 반환 구조가 serializer 친화적이다.

### Phase 3. 테스트 보호막
목표:
- 이후 통합 과정에서도 core가 깨지지 않도록 한다.

할 일:
1. empty rule 테스트
2. no-execution 테스트
3. deterministic ordering 테스트
4. JSON 구조 테스트
5. snippet helper 테스트
6. 더미 규칙 통합 테스트

완료 조건:
1. 회귀를 잡을 수 있는 최소 테스트 세트가 있다.
2. core 수정 시 테스트가 바로 경고를 줄 수 있다.
3. 테스트가 공용 계약의 예시 역할도 한다.

### Phase 4. 병렬 개발 지원
목표:
- C/D/A가 B의 구조 위에서 바로 개발할 수 있게 한다.

할 일:
1. rule 구현 예시 1개 제공 또는 동등한 샘플 제공
2. 호출 예시 제공
3. 계약 변경 시 영향 범위 공지
4. 병합 충돌 예상 지점 정리

완료 조건:
1. 다른 팀원이 B에게 구조를 다시 물어보지 않고 시작할 수 있다.
2. 계약 drift 가능성이 낮아진다.
3. 규칙 구현 예시만 보고도 새 규칙을 추가할 수 있다.

### Phase 5. 통합 대응
목표:
- 규칙/GUI/JSON export가 core와 자연스럽게 합쳐지도록 한다.

할 일:
1. C/D 브랜치와 contract 호환성 확인
2. A가 필요한 호출 형태 점검
3. D의 JSON export와 구조 충돌 확인
4. 회귀 테스트 수행

완료 조건:
1. 통합 병목이 core 때문에 생기지 않는다.
2. 계약 변경 없이 병합 가능하다.

## 6. 정의해야 할 계약 목록
반드시 초기에 명확히 해야 할 항목:

1. Finding 필수 필드
2. ScanResult 필수 필드
3. rule 입력과 출력 형식
4. findings 정렬 기준
5. JSON 직렬화 형태
6. source snippet 추출 정책
7. 예외 처리 원칙
8. 빈 결과 표현 방식
9. 규칙 등록 위치와 등록 방식

## 7. 권장 의사결정
### Finding
최소 필드로 시작한다.

권장:
- `rule_id`
- `line`
- `code`
- `message`

### ScanResult
비결정적 필드 없이 유지한다.

권장:
- `target_file`
- `findings`

### 정렬
권장:
1. `line`
2. `rule_id`
3. `code`

### snippet 복원
권장:
1. `ast.get_source_segment` 우선
2. 실패 시 줄 단위 fallback
3. 공백/개행 정책은 테스트로 고정

### 예외 처리
권장:
1. 초기 단계에서는 규칙 버그를 조용히 무시하지 않는다
2. 정책이 바뀌면 문서와 테스트를 함께 수정한다

## 8. 리스크 관리
### 리스크 1. 계약 과설계
대응:
- 최소 필드로 출발
- 추측성 필드 추가 금지

### 리스크 2. 규칙별 하드코딩
대응:
- 공통 인터페이스만 제공
- 규칙별 로직은 rule 모듈에 남긴다

### 리스크 3. 비결정성 유입
대응:
- 시간/랜덤/환경값 사용 금지
- golden JSON 테스트 고려

### 리스크 4. 병합 충돌
대응:
- 계약을 먼저 고정
- 변경 시 즉시 팀 공유

### 리스크 5. 근거 코드 품질 저하
대응:
- snippet helper 테스트 추가
- fallback 정책 명시

### 리스크 6. 소비자 불일치
대응:
- A와 D가 실제로 필요한 형태를 조기 확인
- contract translation이 필요하면 core 설계를 재검토

## 9. 완료 정의
B 작업은 아래를 만족하면 완료로 본다.

1. 공통 계약이 문서와 코드에서 명확하다.
2. `scan_file(...)`가 동작한다.
3. AST 기반 비실행 분석이 보장된다.
4. 규칙을 꽂을 수 있는 구조가 있다.
5. JSON 구조가 안정적이다.
6. 테스트가 통과한다.
7. 담당 외 영역을 침범하지 않았다.
8. 다른 팀원이 바로 붙을 수 있을 정도로 계약이 설명 가능하다.

- 다음 작업: serializer 고정 및 no-execution 테스트 보강
- 바로 사용할 수 있는 공용 인터페이스: `scan_file(path)`, `Rule.check(...)`
- 계약 변경 영향 대상: C, D

## 12. AI에게 줄 때 기대하는 작업 순서
이 문서를 받은 AI는 아래 순서로 움직이는 것이 바람직하다.

1. 전체 문서 우선순위를 재확인한다.
2. B의 범위와 비범위를 요약한다.
3. 공통 계약 초안을 먼저 제안한다.
4. 그 계약을 기준으로 core 스켈레톤을 작성한다.
5. 테스트를 함께 작성한다.
6. 담당 외 영역 변경은 피하고 필요한 연결점만 명시한다.
