# B-PRD.md

## 1. 문서 목적
이 문서는 착한코드검거단 프로젝트에서 팀원 B의 담당 범위를 제품 관점으로 고정하는 전용 PRD이다.

팀원 B는 최종 사용자에게 직접 보이는 화면이나 개별 탐지 규칙보다 먼저, 프로젝트 전체가 의존하는 공통 계약과 분석 엔진의 기반을 만든다. 따라서 이 문서의 목적은 B가 무엇을 만들어야 하는지뿐 아니라, 무엇을 만들지 말아야 하는지도 분명히 고정하는 데 있다.

본 문서는 저장소 루트의 `PRD.md`, `AGENTS.md`, `plan.md`를 대체하지 않는다. 충돌 시 우선순위는 항상 다음과 같다.

1. `PRD.md`
2. `AGENTS.md`
3. `plan.md`
4. `B-PRD.md`
5. `B-AGENTS.md`
6. `B-plan.md`

B 전용 문서는 원본 명세를 B의 작업 범위로 구체화한 실행 문서다.

## 2. B의 역할 정의
팀원 B는 Core / Shared Contract / AST Infrastructure를 담당한다.

B의 목표는 다음 세 가지를 가장 먼저 안정적으로 고정하는 것이다.

1. 공통 데이터 계약
2. AST 기반 단일 파일 분석 흐름
3. 규칙이 올라갈 수 있는 확장 가능한 공용 기반

B는 개별 탐지 규칙의 내용보다 먼저, 다른 팀원이 안전하게 병렬 개발할 수 있는 바닥 구조를 제공해야 한다.

즉, B는 다음 질문에 대한 공통 답을 코드와 문서로 확정해야 한다.

1. Finding은 어떤 필드를 가져야 하는가
2. 분석 결과 전체는 어떤 구조여야 하는가
3. 규칙은 어떤 입력을 받고 무엇을 반환해야 하는가
4. 분석기는 어떤 흐름으로 파일을 읽고 AST를 만들고 규칙을 실행하는가
5. 결과를 어떻게 항상 같은 순서와 형태로 내보내는가

## 3. 제품 맥락
프로젝트 전체는 사용자가 선택한 Python `.py` 파일 1개를 실행하지 않고 정적 분석해서, 코드 안에서 확인 가능한 긍정적 시큐어 코딩 패턴만 Finding으로 보여주는 Windows 데스크톱 프로그램이다.

B는 이 전체 제품 중 다음 제품 하위 영역을 책임진다.

- 단일 `.py` 파일 읽기
- Python 표준 `ast` 파싱
- 규칙 공통 인터페이스
- 규칙 실행 파이프라인
- Finding/ScanResult 공통 구조
- 결정적 JSON 직렬화 기반

## 4. B 범위의 목표
### 필수 목표
1. `Finding` 구조를 확정한다.
2. `ScanResult` 구조를 확정한다.
3. `Rule interface`를 확정한다.
4. `scan_file(...)` 중심 분석 흐름을 구현한다.
5. 규칙 등록 및 실행 구조를 제공한다.
6. 분석 대상 파일이 실행되지 않음을 보장한다.
7. 동일 입력에 대해 동일 결과가 나오도록 결정성을 보장한다.

### 구현 관점의 목표
1. 규칙 구현자가 분석기 내부 세부사항을 몰라도 규칙을 작성할 수 있어야 한다.
2. GUI가 복잡한 내부 객체를 몰라도 스캐너를 호출할 수 있어야 한다.
3. JSON 저장 담당이 별도 후처리 없이 결과를 직렬화할 수 있어야 한다.
4. 통합 시 규칙 추가 때문에 core 코드를 자주 바꾸지 않아야 한다.

### 산출물 목표
1. 다른 팀원이 의존 가능한 공용 타입/계약
2. 규칙이 꽂히는 AST 스캐닝 엔진
3. JSON 저장에 필요한 안정적 결과 구조
4. core 동작을 보호하는 최소 테스트

## 5. 비목표
다음은 B 범위의 목표가 아니다.

1. GUI/UX 구현
2. GOOD001~GOOD006 세부 탐지 로직 완성
3. 전체 보안 점수 산정
4. 파일 전체 안전성 판정
5. 폴더/프로젝트 단위 분석
6. LLM 기반 해석 추가
7. 네트워크/API 호출 기반 분석
8. 대상 파일 실행 또는 import

또한 다음도 B의 비목표다.

1. 특정 규칙에만 유리한 bespoke interface 만들기
2. UI 표시 전용 필드를 core 계약에 미리 과도하게 넣기
3. 나중에 필요할 수도 있다는 이유로 추측성 구조를 넣기
4. 규칙 엔진을 프레임워크 수준으로 과설계하기

## 6. 핵심 사용자 가치
B가 잘 만든 core는 최종 사용자에게 직접 보이지 않을 수 있지만, 아래 가치를 만든다.

1. 사용자가 선택한 파일을 안전하게 분석할 수 있다.
2. 분석 결과가 항상 일관된 형식으로 나온다.
3. 규칙이 늘어나도 결과 구조와 호출 방식이 흔들리지 않는다.
4. GUI와 규칙 팀이 병렬로 개발해도 통합 비용이 낮아진다.

여기서 B의 품질은 최종 사용자 경험에 간접적으로 큰 영향을 준다. 공통 계약이 흔들리면 GUI 표시 형식, JSON 저장 형식, 규칙 추가 방식이 함께 흔들리므로 전체 프로젝트 속도가 급격히 떨어진다.

## 7. 기능 요구사항
### FR-1. 단일 파일 분석 입력
- 분석 입력은 Python `.py` 파일 1개여야 한다.
- B가 제공하는 core API는 단일 파일 경로를 받는다.

### FR-2. 비실행 AST 분석
- 대상 파일을 실행하지 않고 텍스트로 읽어 `ast.parse(...)` 한다.
- 대상 파일을 모듈 import 하지 않는다.

### FR-3. 공통 계약
- Finding은 최소한 `rule_id`, `line`, `code`, `message`를 포함해야 한다.
- ScanResult는 최소한 `target_file`, `findings`를 포함해야 한다.
- 가능한 한 최소 필드로 시작해야 하며, 모든 추가 필드는 명확한 소비자 요구가 있을 때만 넣는다.

### FR-4. 규칙 인터페이스
- 규칙은 공통 입력 형태를 받아 Finding 목록을 반환해야 한다.
- 규칙은 core 내부 상세 구현에 강하게 결합되지 않아야 한다.
- 규칙은 대상 파일을 다시 읽거나 실행하지 않아야 한다.
- 규칙은 Finding 외의 임의 구조를 반환하지 않아야 한다.

### FR-5. 규칙 실행 파이프라인
- core는 등록된 규칙들을 순서대로 실행할 수 있어야 한다.
- 규칙이 추가되어도 `scan_file(...)` 호출 방식은 바뀌지 않아야 한다.
- 빈 규칙 세트에서도 예측 가능한 결과를 반환해야 한다.

### FR-6. 결정적 결과
- 동일 입력 파일과 동일 규칙 세트에 대해 findings 순서와 JSON 구조는 항상 같아야 한다.
- 결과에는 시간, UUID, 런타임 환경 식별자처럼 실행 시점에 따라 달라지는 값이 없어야 한다.

### FR-7. JSON 직렬화 기반
- 결과는 UTF-8 JSON으로 저장 가능한 구조여야 한다.
- 시간, 랜덤값, 환경 의존 필드는 포함하지 않는다.
- 결과 객체는 직렬화 전에 추가 가공이 거의 필요 없도록 단순해야 한다.

### FR-8. 근거 코드 제공
- 각 Finding에는 사용자가 확인 가능한 근거 코드가 포함되어야 한다.
- 근거 코드는 가능한 한 해당 AST 노드에서 안정적으로 복원돼야 한다.
- 스니펫 복원 실패 시에도 최소한 줄 단위 fallback이 있어야 한다.

### FR-9. 오류 전파 원칙
- B의 core는 규칙 버그를 침묵시키는 구조를 기본값으로 두지 않는다.
- 예외 처리 정책은 문서화되어야 하며, 디버깅 가능성을 해치지 않아야 한다.

## 8. 품질 속성
### QA-1. 결정성
- 결과 순서가 고정돼야 한다.
- JSON 구조가 고정돼야 한다.

### QA-2. 안전성
- 대상 파일 실행 금지
- import side effect 금지

### QA-3. 단순성
- 규칙 구현자가 빠르게 이해할 수 있어야 한다.
- 과도한 추상화는 피한다.
- 팀원이 코드 구조를 설명 없이도 추론할 수 있는 수준이어야 한다.

### QA-4. 확장성
- GOOD001~GOOD006 규칙이 무리 없이 연결돼야 한다.
- 향후 규칙 수가 늘어나도 contract 변경 없이 추가 가능해야 한다.

### QA-5. 테스트 가능성
- 더미 규칙과 fixture로 쉽게 검증 가능해야 한다.
- 파일 실행 없이도 core 동작을 충분히 검증할 수 있어야 한다.

### QA-6. 협업 안정성
- A, C, D가 동시에 작업해도 core 변경 요구가 잦지 않아야 한다.
- 계약 변경이 필요할 때 영향 범위를 쉽게 설명할 수 있어야 한다.

## 9. 권장 계약 초안
### Finding
권장 최소 필드:

- `rule_id: str`
- `line: int`
- `code: str`
- `message: str`

필드 설계 원칙:

1. UI와 JSON 저장, 테스트가 모두 재사용할 수 있어야 한다.
2. 규칙별 특수 메타데이터 의존도를 최소화해야 한다.
3. 사람이 읽는 설명과 기계가 정렬하는 키를 분리해 단순하게 유지해야 한다.

권장하지 않음:

1. `severity`
2. `confidence`
3. `category`
4. `score`
5. `timestamp`

### ScanResult
권장 최소 필드:

- `target_file: str`
- `findings: list[Finding]`

구조 설계 원칙:

1. 상위 구조는 최대한 얇게 유지한다.
2. 결과 해석 책임을 과도하게 담지 않는다.
3. GUI, JSON export, 테스트에서 같은 객체를 공유할 수 있어야 한다.

### Rule
권장 인터페이스 개념:

- 입력: `ast.AST`, source helper
- 출력: `list[Finding]`

규칙 인터페이스가 만족해야 할 성질:

1. 규칙 작성자가 독립적으로 테스트 가능해야 한다.
2. core가 규칙별 조건문을 알 필요가 없어야 한다.
3. 규칙 추가가 스캐너 수정으로 이어지지 않아야 한다.

## 10. 성공 기준
B 범위는 아래를 만족하면 성공이다.

1. `.py` 파일 경로를 받아 AST 파싱이 된다.
2. 규칙 실행 결과를 findings로 모을 수 있다.
3. 결과가 결정적으로 정렬된다.
4. JSON 저장 가능한 구조를 만든다.
5. 규칙이 아직 비어 있어도 스캐너가 동작한다.
6. 최소 테스트로 no-execution과 계약 안정성이 검증된다.

아래 조건도 함께 만족해야 한다.

1. core 코드만 읽어도 분석 흐름이 추적 가능하다.
2. C/D가 예제 규칙 하나를 기준으로 바로 구현을 시작할 수 있다.
3. A가 호출해야 할 entrypoint가 모호하지 않다.
4. D가 JSON export를 붙일 때 별도 contract translation이 필요 없다.

## 11. 외부 인터페이스 기대치
B는 다음 팀원들을 위한 공용 인터페이스를 제공한다.

- A: GUI에서 호출 가능한 단순한 scan entrypoint
- C/D: 규칙만 구현해서 연결 가능한 rule contract
- D: JSON export와 integration에서 재사용 가능한 ScanResult 구조

## 12. 리스크
1. 계약이 늦게 바뀌면 A/C/D 전체가 다시 수정해야 한다.
2. Finding 필드가 과도하면 UI/규칙/JSON 모두 복잡해진다.
3. 비결정적 필드가 들어가면 golden JSON 테스트가 깨진다.
4. core가 규칙별 특수 처리에 물리면 확장성이 급격히 떨어진다.
5. 스니펫 복원 정책이 불안정하면 Finding 근거 품질이 떨어진다.
6. 예외 처리 정책이 모호하면 통합 때 디버깅 비용이 커진다.

## 13. B의 제품 판단 원칙
애매할 때는 아래 순서로 판단한다.

1. 원본 `PRD.md` 위반 여부
2. 비실행 원칙 보장 여부
3. 결정성 보장 여부
4. 팀 병렬 개발에 유리한지
5. 구현 단순성이 유지되는지

## 14. B의 설계 원칙
1. 최소 계약부터 시작하고, 필요가 검증될 때만 넓힌다.
2. 규칙별 특수성을 core가 알지 않게 한다.
3. 결과 해석보다 결과 관찰 가능성을 우선한다.
4. 공용 계약은 읽기 쉬운 이름과 얇은 구조를 유지한다.
5. 테스트가 설명서 역할도 하도록 만든다.

## 15. B의 산출물에 기대되는 읽기 경험
좋은 B 산출물은 다음과 같아야 한다.

1. 새 팀원이 문서와 코드만 보고 바로 구조를 이해할 수 있다.
2. 규칙 구현자는 "어디에 무엇을 넣을지" 고민하지 않는다.
3. GUI 담당은 "무엇을 호출하고 무엇을 받는지" 바로 알 수 있다.
4. 통합 담당은 JSON과 core 사이에서 별도 변환층을 만들 필요가 없다.
